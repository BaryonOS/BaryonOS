# UI and product rules
Read the root instructions and docs/PRODUCT-AND-SOVEREIGNTY.md. Also read docs/DESIGN-AMBITION.md. Label simulations and a functioning OS separately.
Use a consistent, independent product language; copying an existing shell is not the objective. Use familiar patterns where user research supports them.
Assess keyboard operation, focus, scaling, contrast, plain language and assistive technology. Permission messages must identify concrete objects and consequences; avoid endless permission dialogues.
An app must not be able to convincingly imitate the trusted system dialogue; describe the compositor/input boundary. Configurability must not silently disable security. Privacy explanations may be switched off, but the capability decision and Security Floor remain independently active.
Do not offer a mandatory vendor cloud or OS telemetry. Present Mijn NAS (My NAS), Ruimte ontvangen (Receive space) and Ruimte aanbieden (Offer space) within the same OS concept; an explicitly selected external storage provider may additionally store only opaque client-side encrypted objects under docs/implementation/ENCRYPTED-OBJECT-STORAGE.md. Provider storage is not a silent fallback and receives no Nieuw OS content key. Pairing must be straightforward with verified identity, LAN by default for personal NAS and separate permission for internet access. When receiving space, explain that the administrator can erase their NAS copy without consent but receives no decryption key. Administration displays quota/usage metadata, not guest documents. An administrator confirms their own deletion; the guest need not approve it. Label browser mocks and actual encryption experiments separately. AI runs exclusively on the device, with no cloud fallback. Make combined file/NAS/internet permissions for third-party apps understandable and revocable. Do not mandate accounts or AI. Make advanced settings discoverable and recoverable. Measure task completion with real users before making usability claims.
