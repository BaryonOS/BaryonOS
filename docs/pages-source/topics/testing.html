Why are evidence levels separate?

Every result answers a bounded question for a source version, configuration and environment. Combining unlike results into one vague “tested” label would overstate what is known.

  • Host testChecks selected code or a prototype on the development OS; it does not establish execution under the Baryon OS kernel.
  • Build checkShows that selected sources compile; it does not establish runtime behavior.
  • Native QEMUChecks guest behavior in a recorded virtual profile; it does not establish physical-device support.
  • Physical or humanApplies to the named hardware or review/task scope and cannot be generalized silently.

What makes evidence traceable?

A useful record names the source commit, commands, exit status, profile, expected markers, logs and limitations. Native smoke acceptance requires the documented guest markers and exit behavior, not simply a process that ended without visible errors.

How does evidence affect the roadmap?

A fixed criterion earns points only after every clause and required evidence level is accepted. Partial implementation, more test cases or a second AI review does not award partial points. A regression can reopen a criterion.

What does review not prove?

Automated review can identify defects; it is not an independent human security or accessibility audit. A simulation can inform interaction design but cannot prove native enforcement. Missing evidence remains open rather than being inferred from a similar component.
