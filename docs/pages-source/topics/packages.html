How is package provenance checked?

The current verification core binds a versioned manifest to an application image and checks its length, digest, ABI range and two signatures against keys from an explicitly selected source. The package cannot name its own trusted key. Verification establishes integrity and provenance under that policy, not safety or permission.

What happens during installation?

The intended installer reserves space, streams the verified immutable image, commits it transactionally and updates a durable catalogue. Interruption and uncertain I/O must fail closed and recover from authoritative state. Installation grants no document, network, device or administrative capability.

How do app updates differ from system updates?

App updates follow selected publisher/source policy and preserve the separation between code and user data. System updates additionally need an authentic boot and distribution chain, safe migration, interruption recovery, downgrade resistance and a valid previous system slot. Both paths require explicit provenance and recovery behavior.

What works now?

Package verification, source policy and host-model transaction/catalogue work exist, while the native installer and full app lifecycle remain open. Signed system update and rollback behavior has accepted evidence for its recorded criterion, but the broader trusted release and physical recovery chain is not complete.
