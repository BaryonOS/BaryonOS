Where does a development task start?

Start from the current branch, source version, working-tree state and project checkpoint. Read the contract and local instructions for the files in scope. Historical designs and old research assignments are context, not automatic permission to replace current code.

How is a task bounded?

One task records a goal, invariant, exact write set, acceptance commands and evidence limit. Ownership must be clear before editing. The smallest complete change reuses existing interfaces and avoids unrelated cleanup, policy changes or weakened validation.

How is a result checked?

Run targeted tests first, then the required project gates. Preserve complete logs and exact exit codes. Review the full diff, fix root causes and keep tests, security, accessibility and failure handling intact. Anything not run stays explicitly marked as not run.

How does work reach the project?

A coherent verified step is committed, pushed and presented as a draft pull request. Hosted checks apply to the current head. Merging follows recorded project-owner decisions, including delegated merge authority for mandated workstreams; a pull request or green build does not itself accept a roadmap criterion.
