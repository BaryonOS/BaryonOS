What is Baryon OS?

Baryon OS is research into an independent operating system. Its own Rust kernel, system services and product experience are developed together, starting with x86_64 and UEFI in QEMU.

Why is it called “Baryon”?

Baryons are composite particles, including protons and neutrons. Their composition is a metaphor for a small kernel, separate services and a distinct user environment forming one system. The name makes no claim about security or stability.

Why develop another operating system?

The documented goal is a privacy-respecting European alternative with the connected, polished experience people expect from a modern computer: find a document, resume work and understand which app can access it. This is a design ambition, not a measured comparison with existing systems.

What does “independent” mean here?

The native boot chain and kernel are developed by the project rather than built on Linux, BSD, XNU, Windows or Android. Independence does not mean that every tool, library, firmware component or device is made by the project.

How is it intended to work?

The product direction keeps everyday desktop conventions familiar while making data location and app permissions easier to understand. The Orbit artwork on this site expresses the visual direction; it is not a running OS.

Will the desktop feel familiar?

Setup, login, windows, a taskbar and search are intended to follow recognisable desktop patterns. Material, called Materiaal in the current implementation, is the model for documents, collections and permissions, not a mandatory home screen.

Who controls files and app access?

Apps are intended to receive bounded, visible permissions for specific files, devices and network destinations. Installation alone must not grant general access. These are design and security requirements; the complete native enforcement and user experience are still being integrated.

Can data move between devices?

The plan permits local storage, an explicitly paired personal or family NAS, and an explicitly selected external provider that stores only client-side encrypted objects. Internet access is separate from file access. Multi-device pairing, native networking and provider integration remain open work, so this is not a shipping synchronisation service.

How far along is the project?

The public roadmap records accepted criteria and their evidence. It is a development measure, not a release date or a claim about safety.

What exists today?

The repository reports an independent boot chain, process and capability infrastructure, services, drivers, an SDK and native UI work. Integration differs between components. QEMU and host test results are recorded separately from physical hardware and human evaluation.

What does the progress bar measure?

It shows weighted roadmap acceptance points from the same generated file as the repository README. A point is awarded only when its criterion meets the required evidence. The score is not a percentage of elapsed time, a security rating or proof that the whole OS works on one device.

Is it ready for daily use?

No. There is no supported production release. The full native test release and physical hardware acceptance remain open. Green CI or a successful individual test does not change that boundary.

Can I run Baryon OS?

The documented exploration route is a disposable QEMU virtual machine for development and testing. It is not an installer for a personal computer.

How can I start?

Set up the pinned tools and firmware described in the development guide. From a checkout of the repository, run the preflight, build and smoke commands in order:

  1. python3 -B tools/preflight.py --strict
  2. python3 -B tools/build.py
  3. python3 -B tools/run.py --smoke

A passing smoke run checks a bounded native path. It is not a complete release or a substitute for the acceptance evidence.

Can I install it or use everyday apps?

No supported installation on a physical PC or phone is available. The SDK and native components are under development; third-party app support is a product goal rather than an available app catalogue.

How can I help?

Questions, careful critique and reproducible reports are useful alongside code. The public contribution guide explains the project boundaries and review process.

I do not write code. Where should I start?

Use Discussions for questions, product ideas and accessibility feedback. Describe the task, what felt difficult and what outcome would help. Search for an existing topic first.

I develop software. Where should I start?

Use Issues for a reproducible defect or a bounded implementation task. Before proposing code, read the contribution guide, relevant architecture and security contracts, and the development and test instructions. A pull request must report what was actually tested.

How do I report a security problem?

Report exploitable details privately through GitHub Private Vulnerability Reporting. Do not place them in a public issue, discussion or log. The security policy explains the route and its current support limits.

How is the source licensed?

Project-owned software listed in the file register is available under the Mozilla Public License 2.0. The register identifies covered files; other components and the project identity have their own terms. Review the licensing scope.
