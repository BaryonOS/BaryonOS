# Key service cryptography dependency record

Status: active build contract for the Key Service and every workspace that
locks it.

## Pinned components and provenance

- `chacha20poly1305 = 0.11.0` provides XChaCha20-Poly1305. The manifest disables
  default features and enables `zeroize`; the crate tag is
  [`chacha20poly1305-v0.11.0`](https://github.com/RustCrypto/AEADs/tree/chacha20poly1305-v0.11.0).
  The tag has no separate GitHub Release object. Its declared minimum Rust
  version is 1.85 and its license is `Apache-2.0 OR MIT`.
- The sole production stream-cipher dependency is `chacha20 = 0.10.2`, with
  default features disabled and exactly `cipher`, `rng`, and `zeroize`
  enabled. The crate is `#![no_std]`, declares Rust 1.85, has license
  `MIT OR Apache-2.0`, and declares no build script. Its reviewed crates.io
  source records upstream revision
  [`6b236b758a0279f64d777797514813b2cb572c8b`](https://github.com/RustCrypto/stream-ciphers/commit/6b236b758a0279f64d777797514813b2cb572c8b).
  The service imports `ChaCha20` and `ChaCha20Rng` from this one crate.
- `cipher = 0.5.2` is a direct production dependency with only `zeroize`
  enabled, and supplies the imported `KeyIvInit` and `StreamCipher` traits.
  This explicit feature is required: `chacha20`'s `zeroize` feature wipes its
  core, but does not enable `cipher`'s `zeroize` feature for the stream wrapper
  and buffered keystream. `cipher 0.5.2` is also `no_std`, declares Rust 1.85,
  uses `MIT OR Apache-2.0`, declares no build script, and records upstream
  revision
  [`f836f71fadb3b975b577a293d57851d044f0a44b`](https://github.com/RustCrypto/traits/commit/f836f71fadb3b975b577a293d57851d044f0a44b).
- `chacha20 = 0.9.1` remains only as the dev-dependency alias
  `chacha20-legacy`. It is an independent compatibility oracle and is never
  imported by production source. The root lock contains it for tests; the
  SDK, standalone keyring client, and standalone random-probe locks exclude
  it from their product graphs.
- The crates.io checksums are
  `9b89e1c441e926b9c82a8d023f6e1b7ae0adcfaa7d621814e4d60789bac751cb`
  for `chacha20poly1305 0.11.0`,
  `65c35e4b699c7e15ccbe7ee35c005e4fc0a278d22238a2857e6ce2dadeda1b06`
  for `chacha20 0.10.2`, and
  `c3613f74bd2eac03dad61bd53dbe620703d4371614fe0bc3b9f04dd36fe4e818`
  for the test-only `chacha20 0.9.1` oracle.

Compile-time trait assertions require both `XChaCha20Poly1305` and the direct
`ChaCha20` object to implement `ZeroizeOnDrop`. Removing either feature must
therefore fail compilation instead of silently weakening key cleanup.

The API change is intentionally narrow: `ChaCha20` continues to use
`KeyIvInit` plus `StreamCipher`, while the maintained RNG is imported as
`chacha20::ChaCha20Rng` and uses `rand_core 0.10`. The dev oracle uses the
0.9.1 crate's re-exported `cipher 0.4` traits so it cannot accidentally share
the production implementation. `kdf_hygiene` compares initial and reseeded
DRBG output byte-for-byte against that oracle. The full locked suite then
checks recovery and persistent export/restore into a cold service instance.
A fixed persistent blob and record ciphertext generated by the exact
pre-migration source at `3cb1e16d0f5f1a91784d0761ec0b5c5d7f60606f` are also
restored and decrypted by the migrated code. The KDF, AEAD format, and
persisted wire format are unchanged.

## Freestanding build contract

The x86_64 freestanding profile has no SSE or AVX state. Its builders pass one
`chacha20_backend="soft"` selector for every production ChaCha use: the DRBG,
maintained RNG, and AEAD dependency all resolve to 0.10.2. They also pass
`poly1305_backend="soft"` for `poly1305 0.9.1`; a `target_os = "none"` compile
without that selector is rejected by an explicit compile guard. The obsolete
0.9-only `chacha20_force_soft` selector is absent from product builders.

Host tests establish API compatibility, published vectors, authenticated
failure behavior, persistent-state invariants, and byte-exact legacy DRBG
output. Locked freestanding builds and object inspection separately establish
the selected backend and absence of SIMD instructions; neither is a claim
about physical hardware behavior.
