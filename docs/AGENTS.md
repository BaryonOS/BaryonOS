# Documentation rules

Documentation describes the actual project state. Label proposals, implementation, test evidence and unknowns separately.
Check technical claims against primary sources, recording title, author/organisation, date/version and URL. OSDev is a supplementary learning index, not a substitute for specifications.
Keep PROJECT-STATE.md current and concise. Record new decisions in DECISIONS.md, with consequences and review criteria. Do not put complete logs in permanent instructions.
Write active public documentation in clear, professional English; technical identifiers remain unchanged. Do not invent claims of resistance to hacking, compatibility or compliance.

## Writing style

Use an impersonal, scientific writing style: professional, precise and testable, with short, coherent paragraphs. Describe objectives, concepts, design choices and findings from the subject's perspective. Suitable formulations include 'Public development has been selected' and 'European orientation refers to'. Do not use I, my or we, or narrate the author's actions. A concrete subject-led sentence such as 'The kernel checks permissions' is equally appropriate; unnecessary passive constructions are not required.
Preserve the meaning, status, date and scope of decisions. Distinguish requirements, proposals, reported experiences, measurements and uncertainties; editorial changes provide no new evidence. Refer to the formal role of project owner only where authority or provenance requires it; the identity is recorded in the central AGENTS.md. Distinguish that role from the OS end user.
Preserve names in author credits, source quotations, technical identifiers, literal UI strings, test data and unmodified evidence archives. Source quotations retain their original wording and speaker; add a clearly labelled English translation when needed. This writing convention supersedes the earlier first-person convention. English is the shared project language; direct conversations may use the participant's preferred language.
