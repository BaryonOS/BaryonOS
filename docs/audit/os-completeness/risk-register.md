# Risicoregister

| Risico | Onzekerheid / impact | Detectie | Mitigatie | Stopcriterium | Eigenaar/expertise |
|---|---|---|---|---|---|
| Driverhoeveelheid en hardwarefragmentatie | Welke apparaten/firmware echt werken is onbekend; boot-/data-/supportverlies kan groot zijn. | Exacte parts list, cold boot, device loss/reset, IOMMU/DMA tests. | Eén ondersteund fysiek profiel kiezen; capabilities, fallback en known issues expliciet. | Geen hardware-supportclaim zonder alle verplichte devices, herstelroute en exacte image op dat profiel. | Drivers/hardware |
| Browser-engine onderhoud | Enginekeuze/licentie/portability en patchcadans onbekend; browser is groot bereikbaar attack surface. | Prototype/ABI/engine feasibility, CVE/patch SLA, sandbox test. | Onderhouden engine evalueren; geen nieuwe engine bouwen; afgescheiden process + network/file portals. | Geen dagelijks internetprofiel zolang securitypatches of process isolation ontbreken. | Browser/security |
| Windows/Linux app- en gamecompatibiliteit | User demand en technische/legale kosten onbekend; overstap kan mislukken. | Prioritaire apps, format fidelity, GPU/anti-cheat/vendor test. | Native apps plus expliciete formats; supportmatrix en export; compat layers later. | Geen compatibiliteitsclaim zonder concrete app/version/test profile. | Product/ecosystem |
| Securitypatching en update-infra | Onderhoudsbezetting, signer governance en delivery niet bewezen; lang-open kwetsbaarheid kan OS onveilig maken. | Rebuild-from-clean, signature/rollback, response drills, dependency age. | Patch ownership, channels, provenance/SBOM, recovery and published response route. | Geen public beta zonder security contact, update ownership en recovery. | Security/release |
| Sleutelherstel en crypto-agility | Verlies/rollback/migratiegedrag onbekend; gebruikersdata kan definitief verloren gaan. | Wrong-key, credential-only, device-loss, tamper, version migration. | Maintained primitives, explicit recovery copies, rotate/revoke, metadata threat model. | Geen persistent personal storage zonder tested recovery and versioned migration. | Crypto/storage |
| Filesystemfout en dataverlies | Echte power-cut/medium failure verschillen van fixture fault injection. | Cold reopen, kill at write stages, corruptions, independent disk oracle, physical fault later. | Keep ACK/Unknown semantics, journal/atomicity, backup/restore. | Geen “durable”/“safe” claim outside tested backend and failure model. | Storage |
| Accessibility/i18n tekort | Native APIs and user needs untested; people may be unable to install/recover. | Keyboard-only/screenreader/zoom/RTL/IME user tests. | Accessibility from shared UI primitives; maintained fonts/shaping/input; recruit users. | Geen beta claim before core tasks accessible and no blocker in recovery/setup. | UI/accessibility |
| Performance/power | Host timings, QEMU CPU, and one VM not representative of device latency/energy. | Predefined workload, repetitions p50/p95, RSS/CPU/energy and soak. | Bounded rendering/scheduling/background work, profile-specific tuning. | Don't claim “smooth/efficient” without measured target, workload, limits. | Kernel/UI/hardware |
| Single-maintainer dependency | Project ownership and sustained security/release staffing uncertain. | Bus factor, review ownership, incident/patch exercise. | Document build/release, reviewers, maintainers, support horizon. | Consumer release stops without ongoing response and maintenance owner. | Governance |
| Insufficient user research | Materiaal advantage and daily usability are hypotheses. | Observed representative task completion, errors, time/help, follow-up. | Run formative then acceptance research; keep familiar interactions where useful. | Do not say preferred, easier or competitive before real user evidence. | Product/research |
| Scope too broad | Kernel, desktop, network, NAS, AI, quantum and compatibility compete. | Dependency queue and integration burn-down by fixed gates, not count of PRs. | Prioritize one integrated critical path; preserve open work visibly. | Stop adding independent visible features while P0 data/security gates fail. | Product/integrator |
| UI before data/auth/update foundations | Screens can create success-shaped promises before services exist. | Map every control to real service and failure response. | Label prototypes; gate UI by capability, persistent storage and service integration. | A required action is not shown as successful without durable acknowledged effect. | UI/integrator |
| Kernel without consumer product | Kernel milestones may not translate into installer/apps/network/recovery. | Track FR-R01/R02 end-to-end task completion. | Integrate vertical user journeys regularly. | Do not characterize kernel test as OS daily-use readiness. | Architecture/product |
| Documentation outruns implementation | Specs/PRs may be mistaken for code or evidence; current status snapshot can age. | Source commit/hash links, matrix validator, link/status review. | Separate design/prototype/native/VM/hardware/human/release labels. | Revoke claim when source version/evidence cannot be reproduced. | Integrator/docs |
| Prototype becomes permanent architecture | Browser/host mocks can dictate security/data contracts without native constraints. | Compare mock service contracts to native capability and failure model. | Keep prototypes explicitly disposable; validate assumptions with small native experiments. | No mock success handler may grant rights or assert production behavior. | Architecture/security |
| Open worktree/PR confusion | Branch results can appear integrated; duplicate or stale branches may cause false audit status. | Exact head/base SHA, merge tree check, clean worktree and artifact source. | One source baseline per claim; don't infer completion from agent status. | Stop claim/merge if tree/content preservation and test binding are unclear. | Integrator |

This is a planning register; it does not assert that a vulnerability, user loss
or hardware fault has occurred.
