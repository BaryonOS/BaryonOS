# Progress measurement — from 0% to an independent daily-use OS

The score is calculated from the fixed criteria register in [progress.json](progress.json). This document defines the meaning of the score, acceptance rules, the current criteria and a source-bound implementation/verification inventory. Task execution history remains in the existing project checkpoint and ledger.

Historical progress updates through 9 November 2026 are preserved in [PROGRESS-updates-through-2026-11-09.md](history/PROGRESS-updates-through-2026-11-09.md). Current execution context is recorded in [PROJECT-STATE.md](PROJECT-STATE.md).

## Meaning of the percentage

The denominator is a fixed set of **100 weighted acceptance points**. A point is awarded only when the corresponding criterion is fully accepted with the required evidence.

The percentage is **not** elapsed development time, a security score, a probability of release success, or a claim of parity with Windows, macOS, Linux, or another operating system.

**0%** means that none of the fixed criteria are accepted. **100%** means that all criteria required for a maintainable independent daily-use OS on documented supported hardware are accepted.

## Evidence and acceptance

Evidence levels remain separate. Host tests and prototypes can support a design or implementation claim, but they do not replace a required native QEMU run, physical-hardware test, user study, or independent review.

A criterion is either **Accepted** or **Open**. Partial implementation does not receive partial points. A regression can return an accepted criterion to Open.

The machine-readable source of truth is [progress.json](progress.json). `tools/progress.py --check` validates the score, evidence references, and generated README/rubric/SVG views; it does not determine whether the evidence itself is technically sufficient.

## Reading the three views

**Acceptance** covers the complete fixed 100-point roadmap. **Implementation**
records whether each explicitly scoped requirement in the review is implemented,
partial, missing or unknown. **Verification** names the evidence actually
available for that scope: source inspection, host tests, target build, native
QEMU, physical hardware or human evaluation. A native fixture can be implemented
and tested while its wider user-facing criterion remains open.

The inventory is a dated review, not another backlog or a second completion
percentage. Its requirements are unequal in size and do not represent the full
effort remaining. Counts must not be compared across changed decompositions.
The 24 November review covers all 30 criteria that were open on source
`2eb1c63d2afdf658f0e71d31f3542e320a7dd041`; the 21 previously accepted criteria
retain their existing evidence. B01 is accepted following that reassessment.
The other 29 remain open with explicit outstanding clauses.

The inventory carries its own date and full source commit. Updating the current
task assessment does not silently refresh that snapshot. A material implementation
or verification change requires review of the affected rows and their references;
changing the inventory alone never awards points. The generator checks that every
currently open criterion has a row, references resolve locally or name an allowed
GitHub source/run/PR, and evidence claims carry references. It does not fetch
remote evidence, run the OS or authenticate the technical content of a claim.
