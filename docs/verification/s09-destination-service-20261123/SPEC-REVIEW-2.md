## Findings

### F1 (required)

- **Location:** S09-DESTINATION-SERVICE.md 2.1 (lines 81-92), 2.7 'Carrier of the read-only state' (506-515), section 9 item 3 (line 1105)
- **Finding:** The refutation of review item 3(a) rests on a false claim about main. Section 9 says 'on main no profile can re-grant block authority in the same boot', and 2.1/2.7 conclude that no instance in the same boot can regain the destination grant, so an in-memory latch is enough. On origin/main 035b44e5, kernel/src/m2/m3/m5.rs:260-279 (bind_service) runs create_block_device again on every kernel-driven restart (poll, m5.rs:784-794, restarts <= 3). Kernel profile code can therefore re-create a manifest grant in the same boot. Two things hold the latch argument up: the absence of TRANSFER, which N18 tests, and an unstated rule that the destination profile never re-runs its grant code. No rule states the second, and no N row kills its violation.
- **Fix:** Add an explicit rule: the destination block object is created exactly once per boot, and no kernel restart or rebind path in the destination profile re-creates it or re-runs the service's grant. Add an N row, native at R5 and host-modelled where possible. After the destination service exits, block_objects, nodes and handles for the destination scope never increase. The killing mutation is a profile that re-runs the grant on restart, in the M5 pattern. Correct the section 9 item 3 text so that it states the conditional basis instead of 'no profile can'.

### F2 (required)

- **Location:** N13 (line 855) vs 2.2 check order (lines 127-153)
- **Finding:** N13 expects 'CREATE, APPEND and SEAL on any bound lane Io -12 (failed-mount state takes precedence, check 7 of 2.2)'. Check 6 (operation permission, Access -5) precedes check 7, which gives three different results. (a) CREATE/APPEND/SEAL on a bound verify or restore lane is Access. (b) A second CREATE on the export binding that issued the SEAL is Access. (c) Under 2.7 the export lane 'accepts only INFO and LIST' after resolution, which is Access for the rest. A test written to N13 would fail against an implementation that follows 2.2, and N28 tests the opposite order. Review item 9 asked for exactly this kind of conflict to be removed.
- **Fix:** Rewrite the N13 failed-mount expectations per lane and binding. Expect Access -5 wherever check 6 refuses the operation (verify/restore lanes, a second CREATE, a binding limited to INFO/LIST), and Io -12 only for requests that pass checks 1-6. State whether an *unknown* export binding is limited to INFO/LIST by check 6 or by check 7.

### F3 (required)

- **Location:** 2.2 header table rows offset 32 and count 52 (lines 119, 123) vs 2.3 rows 5, 9, 10 and check 2
- **Finding:** The header table says count u32 is '0 except LIST cursor', yet BIND and UNBIND carry the lane in count (1..=3). It says offset is 'byte offset (APPEND, READ), else 0', yet SEAL carries offset = total length. Revision 1 makes check 2 validate `count` explicitly and N28/N31 are table-driven, so a conforming validator returns Invalid -1 for every BIND and UNBIND. The contradiction already existed in revision 0, but revision 1 makes tests depend on it.
- **Fix:** In the header table: count = LIST cursor or BIND/UNBIND lane, else 0; offset = APPEND/READ byte offset or SEAL total, else 0. List exactly which fields check 2 validates (including whether offset, entry and aux are checked there or per operation).

### F4 (required)

- **Location:** 2.7 failure paragraph (410-418), completion fence (435-439), safe path (493-496), 2.3 INFO row, 2.6 Format, N24(a), N13, N8
- **Finding:** Check 7 is meant to be the total order of state gates, but several reachable states have no gate. (1) The pre-fence interval. Line 413 says the service remounts 'before it accepts another request', while the fence paragraph and N24(a) expect replies before the fence (CREATE refused, export-lane LIST Unknown with zero records). The safe-path Access 'applies only while the instance's mount or remount FLUSH has completed' (493-495, new in revision 1), so the status of CREATE before the fence is undefined; N13 asserts Access, N24(a) only 'refused'. (2) The blank-candidate state. INFO reports it in 'status/aux' with no defined value (2.4 adds no code), and N8 asserts 'INFO reports blank'. BIND, LIST, CREATE, ABORT and UNBIND replies on a blank scope are undefined. (3) The in-boot state after a FORMAT write or flush error: remount or not, what INFO reports, and what BIND returns.
- **Fix:** Add explicit check-7 gates with codes for the pre-fence state (for example CREATE/APPEND/SEAL/FORMAT Access -5, export-lane LIST Unknown -16, other requests answered or deferred as defined), for the blank state, and for the state after a FORMAT failure. Define the INFO encoding of blank (which field, which value). Remove 'before it accepts another request' or reconcile it with N24(a).

### F5 (required)

- **Location:** 2.7 completion fence (452-469), 4.3 K5 (line 766), 5.2, N26
- **Finding:** Revision 1 models kernel -8 as 'the broker is in reset'. On main, volume.rs:964 returns -8 when `r.resetting || r.error.is_some() || r.policy.phase() != Phase::Ready`. Phase is Prepared/Published/Pending/Complete while any request on either lane is outstanding or unconsumed (virtio-core Phase, lib.rs:520-528), and `error` holds a timed-out result until its owner consumes it. Under main's shared Policy, which is the case the bound is written for, the destination therefore legitimately sees -8 for up to TIMEOUT = 500 ticks (volume.rs:22) while a source-lane request is in flight. The 2 x RESET_TIMEOUT = 20-tick bound turns ordinary source latency into a device Io, which is a terminal failed mount at boot or the safe path for the boot. K5 is defined as 'one virtio Policy per block device', but `resetting`, `error` and `active` are global broker fields (volume.rs:122-130), so K5 as written does not by itself confine -8 to the destination's own reset.
- **Fix:** Either (a) define K5 to make the whole broker state per device (Policy, resetting, reset_deadline, error, active), so that -8 on disk 1 means only disk 1's own reset or unconsumed result, and state that; or (b) set the bound to at least TIMEOUT + RESET_TIMEOUT plus a margin and give the rationale. Extend N26 with a stub that returns legitimate -8 for less than the bound (another lane in flight), which must not trigger Io.

### F6 (required)

- **Location:** Section 7 'PCI slot conflict' (891-899), 4.3 K4 (760-765), R5 row (1084)
- **Finding:** Revision 1 narrows K4 to production profiles, but section 7 still files the virtio-rng/disk-1 slot conflict as 'a kernel or profile change under K4 (O4)'. That item now has no home. It also understates the gap. On main no volume-fixture profile creates an Entropy object (create_entropy appears only in desktop, keyring, nas, network_service, system and window_session), and test-volume-archive-device cannot be combined with native-system (volume.rs:15-18). R5 runs dest-format, which needs an entropy-derived destination ID, yet R5's preconditions (O4 (a) K4/K5 and O4 (b) the B3/B5 amendment) omit this. As written, R5 cannot be executed.
- **Fix:** Add an explicit R5 precondition or owner item: a second PCI slot accepted by kernel discovery, or another entropy source, plus an Entropy object in the test-only destination profile. Classify it correctly (test-profile kernel change, not K4). Alternatively, define a test-only deterministic destination ID for R5, labelled non-product.

### F7 (optional)

- **Location:** N28 (line 870)
- **Finding:** N28 claims 'Kills: any swap of two checks in the validator'. Checks 3, 4 and 6, and the safe-path gate of check 7, all return Access -5 with no state change. Checks 3 and 4 cannot be violated together, because an unbound lane has no bound sender. Swaps among the Access checks are therefore unobservable, and the test cannot fail on them.
- **Fix:** Narrow the claim to swaps between checks with distinguishable outcomes (status, handle count or high-water mark). List the unobservable pairs as equivalent mutants.

### F8 (optional)

- **Location:** N12 QEMU kill clause, section 7 evidence lines (924-928)
- **Finding:** N12 relies on `DEST:IO:FLUSHES` and the recorded flush order to detect a missing barrier natively, but the spec does not say which layer emits them. If the destination service reports them itself, a mutation that drops the flush call but keeps the counter defeats the test. On main the comparable VOLUME:ARCHIVE accounting is kept in the kernel broker (archive_ops per object key). The cut trigger must also be independent of the flush count.
- **Fix:** Require DEST:IO counts and order to come from the kernel broker, keyed by the destination object key, and DEST:HANDLES from the kernel Engine, not from service self-report.

### F9 (optional)

- **Location:** 8.2 R2, R5, R6 rows vs section 6 Level column and section 7 stages
- **Finding:** Route coverage gaps. Rows marked host + QEMU have no route step for their host test (N5, N6, N7, N14 are absent from R2's list). The QEMU levels of N3, N7, N8, N10, N15 and N22, and the stages dest-full and dest-corrupt, are not in any R step except R8's catch-all.
- **Fix:** Assign each host and QEMU level to a named R step, or mark it as an R8 precondition explicitly.

### F10 (optional)

- **Location:** 4.3 'To revoke' (735-742)
- **Finding:** Revision 1 says the dialog 'does not revoke before a reply' except on Io or Corrupt. If the destination service exits, its lanes lose their receiver, maintain closes them, and the dialog's UNBIND send returns kernel Closed -9. No reply ever comes, so the dialog never revokes the portal's lane handles or the coupled volume-side binding (4.1, 3.3).
- **Fix:** State that a kernel Closed (-9) or Revoked result on the UNBIND send also permits the revoke, because no queued request can commit without a receiver.

### F11 (optional)

- **Location:** 2.2 Replies (163-169), N22, check 3/4
- **Finding:** All operation-lane replies go to the portal's reply endpoint, including replies to requests rejected at check 3 or 4 (dialog-sent or on an unbound lane). Such a reply carries a request_id the portal never sent. The portal treats it as Protocol and ends its operation, and repeated rejections can fill the portal's reply queue, so the service drops the portal's genuine replies on Again.
- **Fix:** Specify that requests failing check 4 (and check 1 or 2 from a non-portal sender) get no reply, or route those replies to the dialog. Adjust N22 so that it observes no injected reply at the portal.

### F12 (optional)

- **Location:** 2.7 'Why step 5 mirrors' (533-548), section 9 item 1
- **Finding:** The decline of review 1's mount-time mirror is reasoned only for read errors. Step 5 is justified by decay of the newer copy (reads succeed, validation fails). After a crash between barriers 2 and 3, that same decay exposure (E2 unlisted, next_free rolled back, E2 overwritable) stays open until the next commit, which under the safe path may not happen in that boot.
- **Fix:** Either mirror at mount when the copies differ legitimately (outside the safe path), or state this window explicitly as an accepted residual of the decay mitigation.

### F13 (optional)

- **Location:** 2.1 device rule (94-97)
- **Finding:** The citation 'as archive_grant already checks for the fixture (volume.rs:749-753)' is inaccurate. Those lines check that the volume service's own block handle is on device 0 and is a different object. They do not check that the archive scope is on another device. The fixture places the archive on device 0 at ARCHIVE_FIRST_SECTOR for cases 7-11.
- **Fix:** Cite volume.rs:749-753 as a precedent for comparing scopes by check_block, not as an existing different-device rule.

### F14 (optional)

- **Location:** 2.2 paragraph after check list (153-154)
- **Finding:** 'Only a request that passes checks 1-6 advances the high-water mark; a rejected request leaves it unchanged' contradicts itself: a request refused at check 7 passed checks 1-6.
- **Fix:** Reword it to 'a request refused by checks 1-6 leaves it unchanged; a request refused by check 7 advances it', or choose the other rule and adjust N17 and N28.

### F15 (optional)

- **Location:** 2.7 -8 bound time source (466-469), N26(b)
- **Finding:** The -8 bound needs a userspace monotonic time source. None was found in the volume-fixture syscall set, and the spec defers it to R2, so this may be a hidden kernel or profile dependency. N26(b) also chains two bounded waits (barrier 2, then the remount FLUSH), while 2.7 says UNBIND is served 'after at most that bound'.
- **Fix:** Name the time source, or list it as an R5 kernel dependency. State UNBIND latency as at most two bounds in N26(b).

## Verification of review 1 (task S09-DEST-V1, before revision 1)

- **Item 1:** confirmed. Spec 2.6 mount rule (S09-DESTINATION-SERVICE.md:197-203) covers only valid/invalid copies; the only I/O-failure rule is for the mount FLUSH (213-238). Step 4 targets 'the slot holding an invalid copy' (273-276). So if a read error on copy A (A=n+1 {E1,E2}, B=n {E1} after a crash between barrier 2 and barrier 3, 385-387) is treated as invalid, B wins. next_free then rolls back to E2's first sector, and CREATE reserves first=next_free (261), so it can write into E2's extent. If a later mount reads A successfully, a listed E2 fails VERIFY, which violates N12 ('never a listed E2 that fails', line 633). The review's extra demand to mirror before the next CREATE is not needed once a read error is terminal: the next commit already targets the lower-sequence slot and then mirrors (274-277, 386-387).
- **Item 2:** partly. Lines 280-288: an Io, Timeout or Unknown in step 4 or 5 gives a service reply Unknown and a remount. CREATE is barred before resolution 'nor, under the safe path below, for the rest of the boot'. The safe-path trigger (338-341) reads 'after any `Unknown` on a destination write or flush', and its parenthesis about timed-out entry writes indicates the device-level result. On that reading a device Io at barrier 2 or 3 resolves and readmits CREATE, and the 'provisional, confirmed only after cold boot + VERIFY' rule (361-366) does not apply. The wording is ambiguous rather than definitively wrong: it could also mean the service's Unknown reply. N13 (634) lists only Timeout/Unknown. 2.5 (151-155) discards on 'any write error' without the safe path, and has no edge for a Timeout of the step-3 readback (a READ, which the broker reports as -13, volume.rs:1089-1093). Line 221 itself says a failed FLUSH gives no evidence about earlier writes. The Linux fsync error-reporting behaviour was not checked.
- **Item 3:** partly. The spec states a requirement without a carrier: lines 355-361 and O9 at 747-751. Lines 225-228 and 300-302, the N13 row and O8 still describe a 'service restart' route. On origin/main, however, no restarted process can obtain block authority, so the in-boot half of the problem disappears. Spawn 0x50 (supervisor.rs:290-383) is type-blind: check_delegation and bootstrap_delegate (capability-core lib.rs:1078-1089, 1458-1487) require TRANSFER on the spawner's node. Yet every block grant in a profile that has spawn carries no TRANSFER: volume.rs:607-622 and 713-724, system.rs:327, desktop.rs:170, window_session.rs:220, nas.rs:192 all use READ or READ|WRITE|FLUSH. Spec 2.1 (56-61) forbids any other holder. Device 1 (test-volume-archive-device) cannot combine with native-system (volume.rs:15-18), and native-volume without native-system does not compile the supervisor syscalls (m3.rs:94-96, 2215). window_session restart (0x53) recreates only the compositor group, not block objects. The single instance can therefore keep the latch in memory; if it exits, no instance in that boot can write. Warm-versus-cold reboot detection and QEMU reset behaviour were not checked; they remain O9 hypotheses. The runner already passes -no-reboot (run_volume.py:309).
- **Item 4:** partly. On main, quarantine marks only the active lane offline (volume.rs:1075-1079, 1068-1072), but Policy::reset_completed(false) sets the shared phase to Quarantined (virtio-core lib.rs:562-568). The other lane then passes its own offline check (volume.rs:961-963) and gets -8 indefinitely at 964-966. Spec 322-325 attributes the 'ends within RESET_TIMEOUT, ready or offline' bound to the per-device broker (K4/K5), however, and R5 already includes the per-device Policy (774) and O4 requires K5 for products (726-727). The wedge exists only on main's shared Policy, which the spec does not plan to use for the destination. The service's single-loop resubmission still has no service-side bound.
- **Item 5:** partly. receive attaches every transferred cap unconditionally and fails on slot shortage before dequeuing (capability-core lib.rs:1568-1586). The head-of-line stall and the unwanted held handle are both real. The portal half is refuted on main: the portal's volume handles are client_send = bootstrap_delegate(..., SEND) and client_reply = derive(..., RECV) (volume.rs:596-601), the child node gets exactly those rights (lib.rs:1478-1485), and the archive block handle has no TRANSFER (713-724). Spec 4.1 (471-473) already says no portal handle carries DERIVE or TRANSFER, and send requires TRANSFER per transferred cap (lib.rs:1512). The only TRANSFER holder in the design is the trusted dialog, through its lane roots (512-513), so the remaining risk is a dialog fault: slot exhaustion or a lane root parked in the service.
- **Item 6:** confirmed. 4.3 (530-536): the service holds SEND only on the portal's reply endpoint. 5.1 (579-583): the dialog holds a control SEND, three lane roots and an intake SEND, but no RECV endpoint. The dialog therefore cannot receive the BIND Ok and UNBIND Ok that 4.3 (537-543) and N6 wait for. N18 (639) says '5.1 handles plus one Entropy object and handle', but 5.1 (580-581) already includes the Entropy handle, so it is counted twice. The service list in 5.1 omits the block handle. Endpoint quotas allow the fix: the dialog owns 0 of MAX_OWNED_ENDPOINTS=4 (lib.rs:1248-1255).
- **Item 7:** confirmed (owner decision). N18 (639) counts only. BLOCK_RIGHTS = BLOCK_READ_RIGHTS|WRITE|FLUSH, and BLOCK_READ_RIGHTS includes DERIVE|TRANSFER|REVOKE (lib.rs:21-22); create_block_device_with_rights accepts it (1374). A count-only check passes with those rights. The rights probe pattern exists at volume.rs:743-748 (ARCHIVE_READONLY_RIGHTS), and a device check exists at 749-753. Spec 1 (47-48) and 2.1 (56-57) permit 'device or partition', which includes a partition on the source device that shares reset and FLUSH with it.

The BIND row (119) says 'aux = new grant generation (> every earlier one for that lane)', but it lists no refusal status (only Ok, NoDevice, NotFound, Busy) and no storage rule. request_id restarts per binding (76). maintain() cancels queued messages only when the endpoint is closed or a carried cap is revoked (lib.rs:1953-1963), so plain portal data messages survive revoke. The single loop's order across lanes is unspecified (545-547). If a re-BIND reuses g, stale queued APPEND or SEAL messages from the same portal pid pass the epoch and request_id checks.
- **Item 9:** confirmed. Line 87 says every field is validated 'before any state is consulted', while line 90 says an unbound lane returns Access 'for every request', which is a state check. N14 (635) expects NoDevice on 'any lane op', but the ID check exists only in BIND (119), unbound lanes return Access (90), and a foreign non-blank layout mounts Corrupt (201-203), whose refusal status is never given ('refuses every operation except INFO'). An absent device: 5.3 (598-600) says NoDevice, but the broker returns -14 to the mount FLUSH (volume.rs:967), which 2.6 maps to the failed-mount state with Io (215-219). Whether a rejected request advances the request_id high-water mark is unstated.
- **Item 10:** partly. Step 4 (272-276) has no validate-before-write rule, and after step 5 a bad copy would be in both slots, which gives Corrupt (201-206). None of the review's three examples is reachable under the spec's own rules: length > 525 328 cannot pass step-3 archive::verify, because walk bounds count and content bytes and requires end of stream (archive.rs:279-292, S09-BACKUP-ARCHIVE trailer rule); next_free > formatted count is blocked by the entry-path scope-end rule (264-267) together with formatted count = sector_count (187); label length 0 is blocked by CREATE name_length 1..=32 (82).
