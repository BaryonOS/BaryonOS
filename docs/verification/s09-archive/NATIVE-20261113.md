# S09 native archive slice: local evidence (13 November 2026)

**Scope.** This file records local evidence for the native S09 slice. The slice covers export, restore, refusal of a damaged archive, restore into a domain with conflicting names, and an export into a target too small for the archive, all using the S09 archive format v1. The archive moves between the volume service and a scoped archive range on the same disposable QEMU test image. This is not S09 acceptance; the criterion stays open.
- Design and limits: [S09-BACKUP-ARCHIVE.md](../../implementation/S09-BACKUP-ARCHIVE.md), section "Native slice".
- Host-level evidence of 5 November 2026: [README.md](README.md).

**`archive-conflict`**
- Image: the same fresh image as for restore, with this pre-state written by the portal before restore:
  - slot 3 holds "Bezet", which occupies an archived slot;
  - slot 6 holds "Herstart", which has the same name as archived slot 4;
  - collection 1 is "Werk", the same name as in the archive;
  - collection 2 is "Anders", a different name from the archive's.
- Guest result: `ARCHIVE_CONFLICT:PASS`, exit 33.
- Archive I/O (reads/writes/flushes): 1440 / 0 / 0.
- The guest report is restored `{1, 2, 5}`, conflicts `{3, 4}`, uncollected `{1}`.
- Host checks:
  - the archive range is unchanged;
  - the expected end state comes from `volume_archive.expected_restore`, which follows the spec and shares no code with `volume-core`. That end state includes at least one slot conflict, name conflict, uncollected object and reused collection.
- What the image shows:
  - the pre-state objects are unchanged at revision 1;
  - slot 4 stays empty;
  - slot 1 keeps its kind (revision 2) but sits outside any collection;
  - slot 2 joins the reused "Werk";
  - slot 5 is restored at revision 1;
  - collection 2 keeps the name "Anders".
- Negative controls, run on the run-9 images: each oracle accepts its own stage's after-image and refuses the other stage's.
  - The conflict oracle refuses the restore image: "object 3 version 1 is not a written fixture".
  - The restore oracle refuses the conflict image: "restored object 1 differs from the archive".
- Two more rules are host tests. Each test fails against its mutant of `restore`:
  - no collection is created for a conflicting object, whether it conflicts by slot or by name. With only two collected objects in the archive, this cannot hold together with the four rules the stage requires;
  - an uncollected object without other metadata stays at revision 1. This fixture does not exercise it, because its uncollected object has a kind.

**`archive-full`**
- Image: the export stage's output with the archive range set back to its canaries. Its SHA-256 equals the input of `archive-export` (`19e2fdb3…`), so the range holds no earlier archive.
- Grant: READ|WRITE|FLUSH on sectors 1000..1100 only, which is 100 sectors; the archive needs 180.
- Guest result: `ARCHIVE_FULL:PASS`, exit 33. The portal:
  - received `Full` from `export` and did not finish the sink;
  - saw a write at sector 100 refused by the kernel;
  - saw `verify` refuse the range with `Corrupt`;
  - listed 5 objects and saw a document write refused with `Access`.
- Archive I/O (reads/writes/flushes): 4 / 100 / 0. All 100 broker writes are archive I/O, nothing was flushed, and the service made 0 commits. The 4 reads are one sector, the header: `verify` refuses at the length bound before it reads further. The kernel counts writes but does not check which sectors were written; only the host compares the 100 sectors.
- Host checks:
  - every sector outside sectors 1000..1100 is unchanged;
  - the 100 sectors equal the first 51 200 bytes of the export stage's 91 801-byte archive;
  - the independent reader refuses both the 100-sector range and the full 1040-sector archive range;
  - the volume oracle still sees the recovered fixture.
- Negative controls, run on the run-9 images:
  - the full-target oracle refuses the export image: "full-target export changed sectors outside the cut range";
  - the export oracle refuses the full-target image: "archive tail padding is not zero";
  - the full-target oracle also refuses one flipped byte in the cut range, and evidence lines that claim 1 flush or 99 writes.
- Host test `full_target_leaves_no_archive_and_a_later_export_over_it_verifies` in `services/volume/tests/archive.rs`:
  - with a target one sector short, `export` succeeds and `finish` reports `Full`, because only the buffered last sector is missing;
  - with half the needed sectors, the stream itself reports `Full`;
  - in both cases nothing is flushed, `verify` refuses the leftover with the cut scope and with a scope that fits, and a later export over the leftover verifies;
  - a `DiskSink` bound that is off by one fails this test.
- Limit: the stage starts from a range without an earlier archive. It does not show that a failed export invalidates an older archive already in the range. An older archive whose leading sectors equal the new stream would still verify, as that older archive.

**AI review findings.** These come from AI review, not an independent human audit.
- Run 4:
  - **`ARCHIVE_ESCAPE`** now counts block objects, nodes and per-process handles, because no handle enumeration exists. The earlier per-handle probes could never fire.
  - **Denial counting.** Calls on the portal's own archive object are no longer counted as app device denials. Run 3 logged 26, 7 and 9 denials, inflated by collect polls; later runs log 6 in every archive stage.
  - **Archive range.** It ends at sector 2040, below the image end, so the capability scope refuses the portal's past-the-end probe; the device size never comes into play.
  - **One flow.** Restore and corrupt share one verify-then-restore flow.
  - **Oracle.** Export compares the created and modified times; restore expects only referenced collections.
- Run 6, conflict stage:
  - The final list check reused step 798 of the preceding `collection_is` check. It now has its own step pair; this changes diagnosis only, not pass or fail.
  - Two restore rules were not covered by the fixture. They are now host tests.
  - Commit `254409b0` said that the fixture had to exercise every restore rule. That overstated it: the runner requires the four rules the fixture can reach.
- Run 7, a read-only verification of documentation and PR claims:
  - The message of commit `b149bf97` said that neither host-tested rule can be reached with this archive. Only "no collection for a conflicting object" cannot be reached together with the four required rules; the other is just not exercised by this fixture. The runner comment and the documents now say this.
  - The PR description said "no `unsafe`". That was wrong: the portal adds one `unsafe` block in `sdk/examples/volume-docs/src/app.rs`, with a SAFETY comment. It borrows the kernel-premapped private 64 KiB RW/NX heap as its archive scratch.
  - Stale comments in `kernel/src/m2/m3/volume.rs` (`archive_grant`) and in the `tools/run_volume.py` module docstring now include the conflict case. Run 7 changes only these comments compared with run 6.
- Run 9, design review of the full-target case before implementation:
  - Step codes were renumbered so that they do not overlap the eight codes `verify_final` uses.
  - The stage input is the export stage's own input, rebuilt and checked by hash, not a new zeroed range.
  - The reader must also refuse the full archive range, which is what a later reader with the normal scope would see.
  - A kernel write probe past the cut scope shows that the bound is enforced by the capability, not only by `DiskSink`.
  - The "later export over the leftover" behaviour is a host test, because the native stage does not exercise it.
