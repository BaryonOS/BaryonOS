# Daily desktop controls: document comparison

The four mature desktops share many interaction patterns but differ substantially in locations, window semantics and system administration; at the checked source version, Baryon OS provides only a small part of these daily routes.

**Status:** research, 2 November 2026. No user test, live OS walkthrough, product proposal or implementation decision. All counts below are **analytical document walkthroughs**. Sources establish described functions, not experienced usability. Additional research dossiers are required for user needs and switching barriers.

## Scope and counting method

- **Windows 11 26H2**, lifecycle entry 2026-09-29 [UI01]; **macOS 27**, explicit version of the Apple guides consulted [UI20]; **GNOME 51 upstream**, released 2026-09-16 [UI40]; **KDE Plasma 6.8**, released 2026-10-14 [UI60]. Manuals are continuously maintained publications and may differ by build.
- GNOME here means the original desktop: Activities overview with dash, no permanent Ubuntu Dock. Ubuntu adds, among other elements, a left dock, desktop icons and minimise/maximise buttons; that variant must not be counted as upstream [UI50]. GNOME Software and KDE Discover assume working distribution backends; GNOME/Plasma are not complete distributions.
- **† KDE documentation limitation:** current `kf6` documentation contains older revisions: Plasma 5.20, Dolphin 22.04 and Audio Volume 5.4. Marked routes are documented routes with version uncertainty, not confirmation of exact Plasma 6.8 pixels. Wi-Fi, audio output and display settings were additionally checked in primary source code at tag **`v6.8.0`** [UI72–74]. Their entry points/labels therefore have more current support; **?** remains where no complete uniform step chain has been established.
- Starting state: signed-in, unlocked desktop; default layout; one screen; known app/filename; supported connected device; Wi-Fi/Bluetooth enabled; necessary accounts/backend already available. No management policy blocks the action. These are **comparison conditions**, not claims that configuration happens automatically.
- One step is one purposeful interaction: opening a menu, activating an item, entering text, confirming, one complete shortcut or one drag movement. Double-clicking to open an object counts as one activation. Waiting, scrolling, pointer distance and reading do not count. **These are not counts of physical clicks or seconds.** A sequence `open → type → Enter` counts as three steps.
- `A(x)=3`: open search interface → type name x → activate the first correct result. Windows: Win; macOS: Cmd+Space; GNOME: Super; KDE: Alt+Space/KRunner. `Q(x)=2` stops after the query. A result other than the first requires additional selection. This familiar route does not establish that a beginner discovers it.
- `+C` means one separate confirmation if shown; `+A` means additional authentication, with a count depending on password/Touch ID/PIN. Network credentials, payments, inserting USB and operating pairing mode are outside the basic count and remain explicit exceptions.
- Different starting states: row 12 begins on a known download page; rows 13–14 in an open file folder; row 15 with file manager open and USB visible; rows 16–19 with suitable windows and two existing workspaces. Their counts must not be added to complete desktop routes to create an OS score.
- English UI labels avoid uncertain translations. Win, Super and Meta refer to the same physical key on many PC keyboards; their system function differs. Mac uses Cmd/⌘ and Option/⌥.

## Interpretation and evidence boundary

**Established from documents:** search, window controls, file management and system status are common functions. Their location and grouping differ. Mac Finder and app/window separation, upstream GNOME without a permanent dock, and Plasma's modules/widgets provide concrete transfer points. This does not establish that one system is easier for everyone.

**Analysis:** identical step counts conceal discoverability, icon recognition, motor demands, keyboard knowledge, index quality and error handling. Configuring accounts, drivers, package sources or corporate permissions may greatly extend the routes. Therefore no average, winner or “x% faster” claim. The `?` cells first require a reproducible walkthrough on the stated release.

**Targeted KDE source check:** at `v6.8.0`, the Networks applet opens a connection list; the network row provides Connect/Disconnect and distinguishes saved connections from new passwords. Audio Volume opens with a speaker icon and retains Devices/Applications as the previous tab. With multiple output devices, radio buttons set default output; Space/Enter work on the device delegate. KScreen registers Display Configuration under category `display`, with a Resolution selector where multiple modes exist; its Keep/Revert dialogue counts down from 15 seconds and initially focuses Revert. This confirms code behaviour and labels, not a working hardware connection, visible result or full accessibility. Total counts remain open: this limited source check does not establish all shell- and backend-dependent interactions. [UI72–74]

**Hypotheses to test:** users confuse closing with quitting, search the wrong scope or miss a hidden chevron. Investigate this with task scenarios, beginners and switchers, predefined success criteria, error recovery and keyboard/screen-reader controls. A short route without accessible focus or explanation may work less well than a longer one.

**Baryon OS, repository inference:** RB-01 is exactly development source `1f0dd9c93959e3b1335656da1e548525a288133e`, not this research branch on main. The scene contains two fixed windows with focus, dragging and dock selection. Session search matches a fixed Materiaal reference. Native clipboard is bounded text transport, not general file copying. N01, compositor recovery, host models and preview account screens do not automatically fill missing consumer routes. This dossier repeats no native acceptance tests and makes no phase 5–8 design decision.
